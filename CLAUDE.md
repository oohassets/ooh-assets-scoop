# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

SCOOP OOH Assets is a Progressive Web App (PWA) and Firebase-hosted dashboard for managing out-of-home (OOH) advertising assets and campaigns across Qatar. It handles campaign booking, digital/static asset inventory, rate cards, and AI-powered assistance for SCOOP Media and Communication.

- **Live app:** https://oohassets.github.io/ooh-assets-scoop/
- **Firebase project:** `scoopassets`
- **RTDB:** `https://scoopassets-default-rtdb.firebaseio.com/`

## Commands

There is no root `package.json`. All commands run from `functions/`:

```bash
cd functions && npm install        # Install dependencies (Node.js 20 required — see firebase.json's runtime)
npm run serve                      # Start Firebase emulator (functions only)
npm run shell                      # Interactive functions shell
npm run deploy                     # Deploy functions to Firebase
npm run logs                       # Stream function logs
firebase deploy --only hosting     # Deploy frontend (no build step — deployed as-is)
firebase deploy --only database    # Deploy database.rules.json (RTDB security rules)
firebase deploy                    # Deploy everything
```

There is no build step, test runner, or linter configured. The frontend is vanilla HTML/CSS/JS deployed directly.

## Architecture

### Frontend (Vanilla ES Modules, No Framework)

The app uses client-side routing with dynamic module imports — there is no bundler. All JS is ES2015+ modules loaded natively by the browser.

**Boot sequence:**
1. `index.html` initializes Firebase Auth and registers the service worker
2. `assets/js/app.js` runs auth guard, then calls `router.loadFromURL()`
3. `router.js` maps `?page=` / `?map=` URL params to view modules and HTML templates
4. `switchView()` calls `utils.js`'s `loadPage()`, which fetches the page HTML, injects any `<style>` blocks found in its `<head>`, and swaps `#app-content`'s innerHTML to the page's `<body>` contents (non-module `<script>`s are re-executed). `switchView()` separately loads the page's CSS file via a `<link>` (if a `cssPath` was passed) and dynamically `import()`s the view module, calling its `init(userName)` export.

**View module contract** — every file in `assets/js/views/` must export:
```javascript
export async function init(userName) { /* setup, fetch data, render */ }
export function cleanup() { /* remove listeners, teardown */ }
```
`router.js` calls `cleanup()` on the outgoing view before loading the next one.

**`home.html`** is the true pre-auth entry point (outside the SPA/router entirely, and outside `login.html` too — `authGuard.js`'s `requireAuth()` redirects here when there's no signed-in user, for every consumer of that shared guard: `app.js`/`index.html` and standalone tool pages like `pages/asset-dimension-checker.html`). It's a plain hero with three buttons — "Login as Scoop" (`./login.html`), "Login as Client" (`./client-portal/login.html`), "Login as Supplier" (`./supplier-portal/login.html`) — no auth guard of its own, no SPA involvement, styled off `assets/css/splash.css`'s existing hero visual language (photo background/tint/glass panel) plus its own `assets/css/home.css` for the role cards and the standalone-page `min-height`/theme-toggle bits `splash.css` doesn't need (that file's version is scoped to sit below the app's fixed 64px nav, which doesn't exist here). GitHub Pages always serves `index.html` at `/` with no server-side rewrite support, so this redirect (not a hosting-level change) is what actually makes the hero the effective entry point.

**`login.html`** is the Scoop staff sign-in page, one hop past `home.html` — it still follows the same external-CSS/JS convention as every routed page: styles live in `assets/css/login.css`, behavior in `assets/js/login-ui.js` (theme toggle + password-visibility toggle + Enter-key handling, `type="module"`) and `assets/js/login.js` (Firebase Auth sign-in only — kept separate so auth logic doesn't mix with page UI wiring). The theme toggle reuses the shared `theme.js`'s `initTheme()` rather than a page-local reimplementation — its button/icon just need the same ids `index.html`'s own nav dropdown toggle uses (`userThemeToggle`/`userThemeIcon`) for `initTheme()` to wire up automatically — so the choice persists to `localStorage` and carries into the app after sign-in, instead of resetting. `home.js` reuses the same `initTheme()` on `home.html` for the same reason.

**Map mode** is an alternative to page mode: `setMap(key)` hides `#app-content`, shows the `#mapFrame` iframe, and updates the info card with asset rates. Navigating to any page restores content and hides the map. `setMap()` skips reassigning `mapFrame.src` (which would force a full reload of the Google My Maps embed) when the URL isn't actually changing — e.g. re-clicking the same location, or navigating away and back to it.

**App loading overlay** — `#appLoadingOverlay` (a spinner absolutely positioned over `.map-container`, styled in `layout.css`) covers the gap between the page becoming visible and the first view/map actually finishing loading. `app.js` hides it after `loadFromURL()` resolves, unless that resolved into map mode — in that case `router.js` hides it itself via a `load` listener on `#mapFrame`, since the Google Maps embed is still loading async at that point. Any element meant to only show during an active map view (like `.map-overlay`) should default to `display:none` in CSS rather than relying on JS to hide it first — otherwise it flashes visible during this same gap.

**JS-toggled visibility never uses inline `style=`** — an element whose show/hide is driven by JS gets its default-hidden state from a CSS rule (or class), not a static `style="display:none"` attribute in the HTML (flagged by this project's editor linter as both an accessibility/maintainability issue and, for a couple of elements, a real flash-of-content risk). The pattern: JS always sets an *explicit* value on toggle (`"block"`/`"flex"`/`"none"`, never `""` to defer back to the cascade), so the static markup only needs to encode the initial state — see `#mapFrame`/`#app-content` (plain `display:none` in `layout.css`, since nothing else styles their `display`), `#calendarSection` (`.cal-section-hidden` in `bookings.css`, toggled via `classList` in `bookings.js`'s tab handlers), `.ci-hidden` (`content-inventory.css`, shared by the Static/Activity/Logs tab sections and `#logsActionsTh`'s admin-only column), and `.notif-badge-hidden` (`navigation.css`, toggled in `notifications.js`'s `updateBadge()`). When the element already has a competing same-or-higher-specificity rule for `display` (e.g. a base `#id{...}` rule, or — worse — a `@media` override that unconditionally re-sets it, like `#calendarSection`'s mobile bottom-sheet layout), the hidden-state rule needs a compound selector (`#id.hidden-class`) or `!important` to reliably win regardless of source order — don't assume a bare `.hidden-class { display:none; }` is enough.

**Splash is the default landing page** — `loadFromURL()` falls back to `openSplash()` (not `openHome()`) when there's no `?page=`/`?map=` param, i.e. right after login. `pages/splash.html` is the marketing hero (Pearl Island photo background, brand-tinted glass panel, "Get Started Booking" / "View Media Contents" CTAs) that used to live at the top of `dashboard.html`; `dashboard.html` now starts directly at the stats grid. `openHome()` still means "go to the Dashboard" (nav-center's "Dashboard" link, dock's home icon) — it does not mean splash.

**Nav right-side swap** — `navigation.js`'s `setNavPageTitle(title, sub)` toggles what's shown on the right side of the top nav: on Dashboard/Splash it's the chatbot/notification/avatar icon cluster (`.nav-actions`); on every other page (Bookings, Content Inventory, Vehicle Traffic, map views, etc.) it's replaced by that page's title + subtitle (`#navPageTitle`, absolutely positioned over the same spot). Every `open*()`/`setMap()` function in `router.js` calls this — call it with `(null)` for icon mode, or `(title, sub)` for title mode when adding a new page.

**Circuit Map panel (Add/Edit Booking)** — a MapLibre GL JS map (`assets/js/circuit-map.js`) embedded in the booking modal, entirely separate from the Google My Maps `setMap()`/`mapFrame` system used elsewhere in the app. On desktop (≥900px) it reveals alongside the form via a `flex-basis` transition (0% → 58%); on phones/tablets (<900px) it goes fully `position:fixed` fullscreen with its own back button instead. Two things to not regress if you touch this:
- Don't size the desktop reveal with `aspect-ratio` + an animated `max-width` again — that combination silently collapsed the panel to 0 width on Safari/iPad (the form would visibly expand to fill the space instead). Plain `flex-basis` has no such issue.
- `.bk-modal` has `overflow:hidden`, which clips a `position:fixed` fullscreen child unless the modal *itself* also goes edge-to-edge at that same breakpoint — see the `:has(.bk-main-row.bk-map-open)` rule in `bookings.css` (scoped so a tablet just filling out the form, map closed, still gets the normal centered modal).
- The date picker (`#bkPicker`) lives inside `.bk-view` (which has `position:relative` for this reason), not as a sibling of `.bk-main-row` — otherwise it inherits the widened modal's full width once the map panel is open instead of staying scoped to the form.

The map has three view modes (`mapMode`: `3d`/`default`/`satellite`, switched via a `<select>`, `applyMapMode()`) — exactly one basemap is visible at a time, and `default` is what loads first. Only the `3d` mode's vector "liberty" style can be forced to English labels (`anglicizeVectorLabels()`, rewriting `text-field` to prefer OpenMapTiles' `name:en`); `default`/`satellite` are raster tiles with labels baked into the tile images, so they can't be relabeled. The "Show Details"/"Show Dimensions" floating panels list selected circuits with a category-color dot (`colorFor()`/`circuitDot()`, matching each circuit's marker color); `DIMENSION_COLLAPSE_GROUPS` merges circuit families that all share one physical dimension regardless of which specific circuit is selected (light poles, TPI Digital Mupi, TPI Monoprix, Mupi Port Arabia Boardwalk, Gewan Crystal Walk) into a single row.

`captureScreenshot()` exports a fixed 5:3 PNG floored at Ultra HD resolution (`EXPORT_MIN_WIDTH = 3840`), capped at `MAX_DEVICE_PIXEL_WIDTH = 8000` *after* accounting for `devicePixelRatio` — MapLibre's internal canvas is `container width × dpr`, so the floor alone could compound into an excessive buffer on a high-DPI phone. It's framed via `fitToVisible(paddingPx)` called *after* resizing to the export dimensions, not before (fitting against the on-screen panel's own aspect ratio first can crop circuits once the container reshapes); `paddingPx` is scaled up from the on-screen default of 60 to match how much wider the container just got, or a fixed 60px padding would be an almost imperceptible margin against a multi-thousand-pixel-wide capture. A "CIRCUIT MAP | BO - Client - Brand Campaign | Dates" header bar (`drawScreenshotHeader()`) is drawn across the top, sourced from a `getBookingInfo` getter bookings.js passes into `initCircuitMapUI()` — the same pattern as `getSelectedCircuits`, since circuit-map.js has no direct access to the booking form's own fields. The header/card text size (`uiScale`) is deliberately capped at `2`, not left as the raw `(export width) / (on-screen panel width)` ratio: that ratio keeps text the same *proportion* of the image as it is on screen, which sounds right but reads as oversized once you're looking at the actual multi-thousand-pixel image rather than the small panel it came from — capping it keeps text a consistent, modest size no matter how far `EXPORT_MIN_WIDTH`/`SCREENSHOT_SCALE` push the resolution. It saves via the Web Share API where available (`navigator.share` with a `File`), falling back to a download link on desktop — a plain `<a download>` pointing at a data URL is unreliable on iOS/Android and effectively unfindable afterward. The filename (`buildScreenshotFilename()`) is `circuit-map-<BO>-<Client>-<Brand Campaign>-<capture date>.png` — the date is *today's* date, not the booking's own selected date range (which already has its own segment in the header).

**Gotchas when adding/editing a page loaded via the router:**
- A page's own `<link rel="stylesheet">` tags are **ignored** in SPA mode — `loadPage()` only auto-injects `<style>` blocks. Any external page CSS file must be registered as the `cssPath` argument to `switchView()` in `router.js` (see `openContentInventory()`).
- CSS rules on `body` don't apply in SPA mode — only the page's `<body>` *children* get injected into `#app-content`, not a literal `<body>` element. Page-level padding/centering/background must be scoped to a wrapper div instead (see `.vr-page` in `vehicle-report.css`).
- Pages meant to also work opened standalone (outside the SPA — e.g. `pages/asset-dimension-checker.html`, `pages/image-compressor.html`) need to keep their own `<link>`/theme-sync `<script>` for that context *in addition to* being registered with the router for SPA mode.
- New pages need a `setNavPageTitle(...)` call in their `router.js` `open*()` function (see above), or the nav will keep showing whatever the previous page set.
- Mobile dock panels (`.dock-panel`, e.g. `#assetsPanel`/`#servicesPanel`) are a flex column of a fixed `.panel-header` + a separately-scrolling `.panel-body`. Put a panel's actual content inside `.panel-body`, not as a direct sibling of `.panel-header` — otherwise the header scrolls away with the rest of the content instead of staying pinned.
- CSS rules with equal specificity are resolved by **source order, not by which one is inside a more specific `@media` query** — a later unconditional rule for the same selector silently wins over an earlier media-query override for it. Keep breakpoint overrides for a given selector *after* that selector's base rule in the file (see `.info-card` in `layout.css`), or the override can end up dead code that never actually applies.

### Backend (Firebase Cloud Functions — `functions/index.js`)

Three exported functions, all in `functions/index.js`, none requiring any Secrets Manager secret (kept intentionally minimal — a missing/misconfigured secret on any one function blocks `firebase deploy --only functions` for *all* functions, since the CLI validates every function's secrets up front before deploying any of them; `scoopAI` and `chatbaseToken`, an Anthropic proxy and a Chatbase JWT signer, existed here previously but were removed as dead code once the Chatbase widget moved to a standalone embed in `index.html` with no backend call at all). `getClientPortalData`/`getSupplierPortalData` each require a Firebase ID token (`Authorization: Bearer <idToken>`, verified server-side via the shared `verifyAuth()` helper using `admin.auth().verifyIdToken()`) in addition to CORS — CORS only blocks browser cross-origin calls, not direct/server-side requests, so it is not a substitute for auth on its own.

Both functions use the `firebase-functions@^4.0.0` v1-style API (`functions.https.onRequest`/`functions.pubsub.schedule`, not the `firebase-functions/v2` imports), which deploys as **1st Gen** Cloud Functions — Gen 1 does not support Node.js 22+/24 at all, only up to Node 20. `firebase.json`'s `functions[0].runtime` and `functions/package.json`'s `engines.node` must both stay `"nodejs20"`/`"20"` (not bumped to match whatever Node version the GitHub Actions runner itself uses, e.g. `actions/setup-node@v4`'s `node-version: 24` in `deploy-functions.yml` — that's just the CLI's own execution environment, unrelated to the deployed function's runtime) or *creating* any brand-new Gen1 function fails immediately with `Runtime "nodejs24" is not supported on GCF Gen1` — a function that already existed before the mismatch was introduced can still silently keep deploying fine (an update, not a create), which is what made this easy to miss.

- **`checkEndingCampaigns`** — Scheduled function (daily 8 AM Qatar time) that scans RTDB for campaigns ending today/tomorrow and sends FCM push notifications to tokens under `fcmTokens`.
- **`getClientPortalData`** — HTTP POST, the sole data source for `client-portal/` (see below). Verifies the ID token, resolves the caller's `userClient/<sanitized-email>` roster entry via the Admin SDK (bypasses rules), and returns `{ clientName, contactName, circuits, myBookings, otherBookings }` — the caller's own bookings in full, and every other client's bookings stripped to `{ Circuits, Slot, Start Date, End Date, label }` only (`label` is `"Reserve"` for `Status: "Pending"`, `"Booked"` for everything else that isn't `"Cancelled"`, which is dropped entirely). No Client/Brand/BO/Person ever leaves the server for another client's rows.
- **`getSupplierPortalData`** — HTTP POST, the sole data source for `supplier-portal/` (see below). Verifies the ID token, resolves the caller's `userSupplier/<sanitized-email>` roster entry via the Admin SDK, and returns `{ supplierName, contactName, assets }` where `assets` is every `oohassets` row with `type === "Static"`, each carrying its full booking history (`Client`/`Brand Campaign`/`Circuits`/`Slot`/`Start Date`/`End Date`/`Status`, `Cancelled` included — unlike the client portal's calendar-occupancy read, this is a flat informational view, not something computing slot availability). Unlike the client portal there's no per-tenant split to enforce (no "which assets belong to which supplier" field exists on `oohassets`) — the scoping here is by asset `type`, not by caller identity: every authenticated supplier account sees the same Static-only set. No Digital-type asset or booking ever leaves the server for this role.

### Client Portal (`client-portal/`)

A second, deliberately isolated login+dashboard for external clients to view their own bookings and a shared campaign calendar — separate HTML/CSS/JS from the internal app, with no import from `assets/js/` (only `firebase/firebase.js`, which is just SDK bootstrap config, is shared). "Isolated" here specifically means a client account cannot see another client's booking data even from the browser devtools console, which is a server-side guarantee, not a UI one — see the `userClient`/root-`.read` bullets below. `client-portal/login.html` + `js/portal-login.js` sign in via the same Firebase Auth project as staff; `dashboard.html` + `js/portal-dashboard.js` call `getClientPortalData` (never RTDB directly — there is nothing for a client account to read there, see below) and render "My Bookings" (a table) and "Campaign Calendar" (the same circuit/slot × date grid as `bookings.js`'s `buildCalendar()`, rebuilt read-only): the caller's own bars are colored by status (green/blue/amber/gray) with real Brand/Client labels, every other booking renders as a plain red bar labeled `"Booked"`/`"Reserve"`. `assets/js/app.js`'s `loadUserProfile()` treats a `PERMISSION_DENIED` reading `user` as "this is a client account on the wrong page" and bounces it to `home.html` — a UX nicety (so a client who signs in on the internal `login.html` doesn't just see a broken dashboard), not the actual security boundary; the actual boundary is a signed-in account needing a matching `user` row at all now (see the Auth guard note below), not just the `PERMISSION_DENIED` case.

Client accounts are provisioned the same console-only way as `user`: an admin creates the Firebase Auth login (email/password) in the Firebase Console, then adds a matching row under RTDB `userClient/<sanitized-email>` with `id` (the unsanitized email, for admin readability — same convention as `user`'s own `id`), `clientName` (must exactly match, case-insensitive, that client's `Client` value on their `Campaigns_Booking` rows — the only field `getClientPortalData` actually matches bookings on), and `contactName` (the person's display name, shown in the portal's topbar instead of their raw email). No frontend code path writes to `userClient`.

### Supplier Portal (`supplier-portal/`)

A third isolated login+dashboard, mirroring `client-portal/`'s exact structure and isolation pattern one-for-one (own `sp-`-prefixed CSS/localStorage keys instead of `cp-`, same "no RTDB read, one Cloud Function call, hard root `.read:false` for listed accounts" shape) but for external suppliers viewing static-asset bookings instead of clients viewing their own. `supplier-portal/login.html` + `js/portal-login.js` sign in via the same Firebase Auth project as staff and clients; `dashboard.html` + `js/portal-dashboard.js` call `getSupplierPortalData` and hand its `assets` array to `js/portal-map.js`, a MapLibre GL JS map — read-only, no basemap switcher/3D/traffic, just markers + popups — reusing the same KML→GeoJSON technique as `assets/js/circuit-map.js` (`fetch('../maps/{oohassets.id}.kml')`, parsed via `DOMParser` + `toGeoJSON.kml()`), on the same flat CARTO raster basemap `circuit-map.js` uses for its own "Default" view. A missing/failed KML fetch is caught and that one asset is skipped (surfaced as a small notice in the UI, `#spMapNotices`) rather than aborting the whole map. Clicking a marker opens a popup listing every booking on record for that asset (Brand Campaign/Client/Slot/dates/Status) — unlike the client portal, there's no anonymization step here since every supplier account sees the same Static-only, non-tenant-scoped set (see `getSupplierPortalData` above).

Supplier accounts are provisioned the same console-only way as `userClient`: an admin creates the Firebase Auth login, then adds a matching row under RTDB `userSupplier/<sanitized-email>` with `id` (unsanitized email), `supplierName`, and `contactName`. No frontend code path writes to `userSupplier`.

### Firebase Realtime Database Security Rules (`database.rules.json`)

Deployed via `firebase deploy --only database` (or pasted into Firebase Console → Realtime Database → Rules → Publish) — wired into `firebase.json`'s `database.rules` key, so it's version-controlled instead of console-only.

- **Read** is `auth != null` at the root **except for a `userClient`- or `userSupplier`-listed account**, either of which gets a hard `false` — this is what makes the client portal's isolation (see above) an actual server-side guarantee rather than a UI convention: a client account has nothing to read directly no matter what it calls from devtools, full stop. For everyone else this is intentionally broad, not an oversight: `rtdb-root.js`'s `loadRootTables()` does a single shared `get(ref(rtdb, "/"))` full-tree read (used by `dashboard.js`, `bookings.js`, `loadCarousel.js`'s `loadAllTables()`, and the notification bell) — RTDB evaluates a `.read` rule only at the exact path requested, so a request for `/` only ever consults the root's own rule, never a nested one. Setting `.read: false` at root for everyone (as an earlier iteration of this file did) breaks that shared read for **every** role, not just restricted ones — the app went blank for all users, not just non-admins, until this was reverted. Closing this further for internal staff would require moving away from the full-root-read architecture (or at minimum excluding `user`/`fcmTokens` from it), not a rules-only change — treated as an accepted, low-severity tradeoff for now since the only sensitive subtrees exposed by it are `user` (internal staff roster, not customer data) and `fcmTokens` (push tokens, not independently exploitable without the Admin SDK).
- **Write** is `false` at root and re-granted per top-level path, since (unlike read) write grants only need to be explicit at the path actually being written to:
  - `user`: `.write: false` unconditionally — no frontend code writes here (see Data section below); role changes are console-only.
  - `userClient`: `.write: false` unconditionally — same console-only convention as `user` (see Client Portal above).
  - `userSupplier`: `.write: false` unconditionally — same console-only convention (see Supplier Portal above).
  - `fcmTokens/$uid`: `.write` requires `auth.uid === $uid` — each person can only write their own push token (`main.js`'s `initPush()`).
  - `Campaigns_Booking`: `.write` requires the signed-in user's `user/<sanitized-email>/rule` to be `"admin"` or `"sales"` — matches bookings.js's own `canEdit = rule === "admin" || rule === "sales"` gate.
  - `Campaign_Logs`, `assetrate`, `assetmap`, `oohassets`, `vehiclecounts`, and `$other` (a catch-all covering every `d_*`/`s_*` circuit table, so newly-added locations don't need a rules change) — `.write` requires `rule === "admin"`.
  - The role lookup itself (`root.child('user').child(auth.token.email.replace('.', ',')...).child('rule').val()`) chains `.replace('.', ',')` four times, since Realtime Database's rules-language `.replace()` only replaces the *first* occurrence per call — chaining is how multiple dots (e.g. a `first.last@` local part) all get sanitized, matching the key scheme described in the `user` bullet below.

### Data (Firebase Realtime Database)

- Campaign bookings live under keys like `Campaigns_Booking`, `Campaign_Logs`. Rows are keyed by a plain sequential index (same convention as `assetrate`). One record = one circuit — a multi-circuit booking made in the UI becomes one record per circuit, all sharing the same `BO`, `Client`, `"Brand Campaign"`, `"Start Date"`/`"End Date"`, `Status`, and `Person`, but each with its own `Circuits` (a single circuit name, matched against `assetrate`'s `Circuits` field) and `Slot` (numeric, auto-assigned per circuit/date-range to avoid double-booking). `Person` is the booker's initials, not their full name.
- `Campaign_Logs` — an append-only audit log of circuit bookings starting/ending: `Date` (when the log entry itself was made), `Type` (`"Add"`/`"Removed"`), `BO`, `Client`, `Circuits` (the clean location name, e.g. `"Underpass Entrance"`, with the specific `Circuit` appended for static rows), `"Start Date"`, `"End Date"`. Originally populated by an external VBA macro reacting to `d_`/`s_` table changes in the source spreadsheet; the Content Inventory page's admin delete/add-row actions (see `content-inventory.js`'s `appendCampaignLog()`) now also append to it directly, mirroring that macro's logic. Viewed/searched/sorted/exported on Content Inventory's "Campaign Logs" tab.
- `user` — staff roster + role. Rows are keyed by each person's email with every `.` replaced by `,` (RTDB keys can't contain a literal `.`) — e.g. `chris@scoop,assets` — not a sequential index like the other tables; this is what lets `database.rules.json` look a signed-in user's role up directly (`root.child('user').child(auth.token.email.replace('.', ',')...)`), since RTDB rules can only do exact-key lookups, not "find the row where field X equals Y". Each record still carries its own `id` field holding the *unsanitized* email (`chris@scoop.assets`) alongside `name`, `initials`, `position`, and `rule` (`"admin"`/`"sales"`/`"view"` — the client-side permission flag consumed as `window.__currentUser.rule` by `app.js`, gating `canEdit`/`isAdminUser` in bookings.js and `isAdmin` in loadCarousel.js/content-inventory.js). `app.js`'s `loadUserProfile()` is unaffected by the key scheme — it still does a full-table read and scans by the `id` field, not by key — so the sanitized keys only matter to the RTDB rules, not the app code. No frontend code path writes to `user`; role changes are made directly in the Firebase console.
- Asset location keys follow the pattern `d_<location>` (digital) and `s_<location>` (static). Each record under a `d_`/`s_` table may carry an optional numeric `order` field controlling its display position on the Content Inventory page (set via that page's admin drag-to-reorder feature, see `loadCarousel.js`/`content-inventory.js`) — records without one sort after ordered ones, in RTDB's natural order. This is the only field on these tables the frontend writes to; everything else on them is populated externally.
- `d_`/`s_` table rows store `Start Date`/`End Date` as raw `"MM/DD/YYYY"` — same as `Campaigns_Booking` — **not** the `"DD-MMM-YYYY"` form they're displayed in on the Content Inventory page. `loadCarousel.js`'s `formatDateDDMMMYYYY()` converts at *read* time only (its own render-prep loop, or an inline edit's local `rowData` copy for immediate re-render) — never write an already-formatted `"DD-MMM-YYYY"` value. Doing so breaks silently on the next read: `formatDateDDMMMYYYY()` splits on `/`, so a value with none in it returns `"—"`, i.e. the date just disappears.
- `oohassets` — the live circuit/asset definition table `bookings.js` (`computeSlotAssignments()`, `loadCircuitSlots()`) and `circuit-map.js` (`loadNameToIdMap()`) both read for circuit names and slot counts, and the join target for `Campaigns_Booking.Circuits`. Rows are keyed by a plain sequential index, each carrying `id` (the same id space as `assetrate`/`assetmap`, and the KML filename under `maps/<id>.kml` — see the Circuit Map panel notes above), `name` (display name), `type` (`"Digital"` | `"Static"` — what `getSupplierPortalData` filters on), `Circuits` (the exact string matched against `Campaigns_Booking.Circuits`, case-insensitive/trimmed) and `Slot` (max concurrent slots for that circuit). Look up a record by scanning for `row.Circuits === <value>`, never `data[key]` directly, same convention as `assetrate`.
- `assetrate` — rate card table. Rows are keyed by a plain sequential index (`1`, `2`, …), **not** by a slug — each record carries its own `id` field (e.g. `"underpass-entrance"`), plus `category` (`"digital"`/`"static"`), `name`, `faces` (numeric), `faces_screen` (formatted display string), `Rate`, `"Service Fee"`, `Duration`, `Dimensions`. Look up a record by scanning for `row.id === key`, never `data[key]` directly. `Dimensions` is usually one `WxHpx` string, but a few locations (e.g. Gewan Crystal Walk) pack multiple sizes into a single value with no separator between them (e.g. `"512x640px384x640px"`) — see `formatDimensionCell()` in `circuit-map.js`, which splits on each `px` occurrence rather than assuming a delimiter exists.
- `assetmap` — drives the Assets Location mega-dropdown/mobile panel (`maps.js` + `asset-location-menu.js`). Rows: `id` (same id as the matching `assetrate` row — this is how `updateInfoCard()` looks up rate-card data for a clicked location), `name`, `parent_id`, `sort_order`, `map_link` (the Google My Maps embed URL for that id). A blank `parent_id` marks a root/column node (`digital`, `static`, `assets`); everything else nests under its `parent_id`, ordered by `sort_order`. The desktop dropdown renders the full nested tree; the mobile panel flattens it to two levels, promoting a node's children up a level whenever that node's own children are themselves branches (not leaves) rather than rendering it as a dead-end grouping label — see `asset-location-menu.js` for the exact algorithm. The `assets` root's children are `assets-google-map` (routes through `setMap()` like everything else) and `assets-google-earth` (rendered as a plain `target="_blank"` link using its `map_link` instead, since Google Earth's share URL isn't an embeddable `maps/d/u/0/embed` link).
- `vehiclecounts` — per-day vehicle counts per circuit. Each record has `ContentDate` (`"MM/DD/YYYY"`), `ContentTotal`, and `Name` (bucketed by island via substring match — contains `"TPI"` or `"GEWAN"`, not an exact field).
- Date fields are stored as `"MM/DD/YYYY"` strings (e.g. `"3/15/2025"`)
- Campaign status values: `"Live"`, `"BO Signed"`, `"Pending"`, `"Completed"`, `"Cancelled"`

### Styling

- `assets/css/theme.css` — design tokens (CSS custom properties), animations, resets — modify this for global visual changes. Brand color is the red scale `--brand-300` … `--brand-700` (+ `--brand-wash`, `--focus-ring`); backgrounds use `--bg-base/surface/elevated/overlay`; semantic status colors are `--success`/`--warning`/`--error`/`--info`. Older token names (`--accent-indigo`, `--accent-cyan`, `--accent-violet`, `--accent-emerald`, `--accent-amber`, `--accent-rose`) still exist as aliases onto the brand/semantic tokens above (for page CSS that hasn't been migrated) — prefer the new names for new code.
- `assets/css/layout.css` — main grid, dock, sidebar
- Page-specific CSS files (e.g. `dashboard.css`, `bookings.css`, `vehicle-report.css`) are injected dynamically by the router alongside their view module — see the SPA gotchas above for what does/doesn't work in this mode
- `font-family: var(--font-body)` is the default everywhere; `var(--font-display)` is reserved for `.hero-headline` only
- CSS class names are kebab-case; element IDs are descriptive English (`mapFrame`, `app-content`, `campaignTableBody`)
- Text-entry `input`/`select`/`textarea` elements are forced to `font-size:16px` on mobile (`@media (max-width:768px)` in `theme.css`, global) to stop iOS Safari's auto-zoom-on-focus — don't add a new form field below that size on mobile without deliberately opting it back out (see `#bkMapViewSelect` in `bookings.css` for how to exempt a compact, non-text-entry control like a small dropdown).
- **Browser-compat/accessibility conventions** (there's no build-time linter — this project's editor surfaces these live via Microsoft Edge Tools, so they're easy to miss outside that editor): `backdrop-filter`, `user-select`, and `mask-image` all need a `-webkit-` prefixed copy declared *before* the standard property (same value, e.g. `-webkit-backdrop-filter:blur(20px); backdrop-filter:blur(20px);`) for Safari; `appearance` needs both `-webkit-appearance`/`-moz-appearance` before it. `-webkit-overflow-scrolling` is obsolete (Safari 13+ momentum-scrolls natively) — remove it outright rather than "fixing" it, it has no modern replacement. Every `<button>` needs an explicit `type="button"` unless it's an actual form submit button. Every `<select>` needs an accessible name — either a real `<label for="...">` (preferred when there's visible label text nearby, e.g. the booking form's `Status` field) or `aria-label` (icon-only/label-less toolbar filters).

### Deployment & CI/CD

- **Frontend:** `firebase deploy --only hosting` — deploys everything in the repo root except `functions/`, `firebase.json`, and dotfiles
- **Functions:** GitHub Actions (`.github/workflows/deploy-functions.yml`) auto-deploys on push to `main` when files under `functions/` change. Requires `FIREBASE_SERVICE_ACCOUNT` GitHub secret.
- **Database rules:** `firebase deploy --only database` — not part of any CI workflow, manual only. See the "Firebase Realtime Database Security Rules" section above before changing `database.rules.json`; a bad root `.read` rule can silently blank the app for every user (see that section's `loadRootTables()` note), so verify the `user` table's role-lookup keys still resolve before publishing.
- **Service worker** (`service-worker.js`) is versioned via `CACHE_NAME`. Bump it on every significant frontend change — the fetch handler is cache-first with no revalidation, so an unbumped change is silently invisible to any returning user until the version changes. New JS files must also be added to `ASSETS_TO_CACHE` or they won't be precached. The worker also answers a `{type:"GET_VERSION"}` `postMessage` with `{type:"SW_VERSION", version: CACHE_NAME}` — this is what powers the "PWA v___" label in the user dropdown (`app.js`'s `initPwaVersionLabel()`), so the displayed version always matches the currently-active `CACHE_NAME` without needing to be duplicated anywhere.

## Asset Location Naming Conventions

Digital locations are prefixed `d_`; static locations are prefixed `s_`. Key location keys used throughout `asset-rates.js` and RTDB (the `assetmap`/`assetrate` `id` field, not `maps.js` — that file now fetches these from RTDB rather than hardcoding them):
- Digital: `underpass`, `mupi-c1`, `mupi-c2`, `gewan`, `udctower`, `monoprix`, `qqscreen`
- Static (light poles/MUPIs): `lightpoles-me`, `lightpoles-mb`, `lightpoles-mc`, `lightpoles-pa`, `mupi-pa`
